# Changelog

## [1.2.13] — Фикс: убраны отдельные картинки обложек рядом с треками

### Изменения
- **Больше НЕ создаются отдельные файлы обложек рядом с треками** (`cover.jpg` и `<Artist> - <Title>.jpg`). По официальному руководству LADA EnjoY Pro c Яндекс Авто ММС читает обложку только из встроенного тега файла (APIC для MP3, covr для M4A, METADATA_BLOCK_PICTURE для Opus/FLAC) — отдельные .jpg рядом с треком она не читает и просто захламляют флешку. Обложка по-прежнему встраивается в теги файла.

### Почему обложки могут не отображаться на EnjoY Pro (из официального руководства)
- Обложка отображается **только в полноэкранном плеере** (нажмите на название трека внизу экрана); в мини-плеере и списках её нет.
- В настройках есть раздел **USB-плеер**: включите обновлённый плеер и пункт загрузки обложек из интернета (загружаются, если не встроены в файл).
- Поддерживаемые форматы: MP3 (32–320 kbps), WAV, AAC/M4A (до 320 kbps), FLAC 44.1 kHz. Формат **Opus/WebM («Original») не поддерживается** — для ГУ скачивайте MP3 или AAC.

## [1.2.12] — Android: решатель челленджей YouTube + видимые ошибки yt-dlp

### Исправлено
- **Все треки плейлиста падали при скачивании (0 из 14), хотя поиск находил их.** yt-dlp 2026.10.26 решает sig/n-челленджи YouTube скриптом из python-пакета `yt-dlp-ejs`, а в APK ставился только сам `yt-dlp`. Встроенный vendor-набор yt-dlp содержит lib-скрипты только для bun/deno (`yt.solver.bun.lib.js`, `yt.solver.deno.lib.js`) — нужного QuickJS-провайдеру `yt.solver.lib.js` там нет, поэтому локальному рантайму было нечего исполнять. Теперь в APK ставится **`yt-dlp-ejs==0.8.0`** (чистый Python wheel; версия и sha3-хэши `lib`/`core` совпадают с ожиданиями yt-dlp 2026.10.26). Дополнительный сетевой fallback — `remote_components: ['ejs:github']`.
- **Причина ошибки скачивания не попадала в лог.** Из-за `ignoreerrors: True` + `quiet`/`no_warnings` yt-dlp молча возвращал неуспех, и в «Логе» было только «❌ Ошибка: трек». Теперь yt-dlp получает `logger`: в лог идут строки `⚠️/❌ yt-dlp: …` с настоящим текстом ошибки (обрезается до 300–400 символов). При повторной попытке используется дефолтный набор клиентов yt-dlp (кастомный `tv_samsung/visionos/web` убирается); при неудаче логируются `rc` и остатки файлов в папке (`файл не создан (rc=…); в папке: …`).

### Добавлено
- Диагностика перед первой загрузкой: `🧩 Diag: yt-dlp-ejs 0.8.0 — решатель челленджей на месте` либо `⚠️ Diag: пакет yt-dlp-ejs отсутствует`.

## [1.2.11] — Android: надёжный поиск native-библиотек + режим «Плейлист»

### Исправлено
- **`nativeLibraryDir` пуст → yt-dlp без JS-рантайма.** На части устройств `ApplicationInfo.nativeLibraryDir` возвращает пустую строку, и QJS не передавался yt-dlp (диагностика 1.2.10 показала это прямым текстом). Теперь каталог native-библиотек определяется по нескольким источникам: Chaquopy-мост → `/proc/self/maps` (каталоги `/data/app/…/lib/<abi>`, где уже загружены `libpython`/`libchaquopy` — самый надёжный источник) → `LD_LIBRARY_PATH`. Возвращается каталог, в котором реально лежит `libqjs.so`. В диагностику добавлена расшифровка источников (`🔎 Diag: источник maps: …`).
- **Плейлист скачивался как один трек.** Мобильный `start_download()` был жёстко зашит на `mode="single"`, а переключатель «Один трек / Плейлист» из интерфейса никуда не передавался — поэтому плейлист из 14 треков давал «Всего треков: 1». Теперь режим идёт по цепочке UI → `PyBridge.kt` → `start_download(url, fmt, mode)` → `Downloader.download(url, mode, …)`; если режим не передан (старый вызов), он определяется по ссылке: `list=`/`playlist`/`/sets/` → плейлист, иначе один трек. Кнопка синхронизации сохранённого плейлиста всегда передаёт `playlist`.

## [1.2.10] — Android: глубокая диагностика JS-рантайма

### Добавлено
- **Развернутая диагностика в «Логе» перед первой загрузкой.** Раньше проверка отвечала только «libqjs.so не найден или не исполняем». Теперь в лог попадает всё, что нужно для точного диагноза: путь `nativeLibraryDir`, список его файлов, режим доступа и биты F_OK/X_OK файла `libqjs.so`, фактический запуск `qjs --help` (путь yt-dlp определения версии) и `qjs --script` (контракт челленджей: rc=0, пустой stderr, точный вывод).
- Смягчено условие передачи рантайма в yt-dlp: отдаём путь при наличии файла (без требования бита X_OK) — фактический запуск проверяет диагностика; бит X_OK на extracted-библиотеках варьируется от устройства к устройству.

## [1.2.9] — Android: диагностика скачивания + мгновенный экспорт в Загрузки

### Добавлено
- **Диагностика JS-рантайма в «Логе».** Перед первой загрузкой приложение проверяет наш бандл QuickJS тем же способом, что и yt-dlp (`qjs --help`), и пишет в лог ровный результат: `🧩 JS-рантайм найден: QuickJS-ng 0.12.0` либо конкретную причину (не найден / нет права запуска / пробный запуск не удался) — теперь причина падения скачивания видна сразу.

В логе — имя файла: `📁 <name>: сохранено в Загрузки/ShipTones`. Дедупликация работает как раньше.

### Сборка

## [1.2.8] — фикс: скачивание на Android (JS-рантайм QuickJS) + экспорт в Загрузки

### Исправлено
- **Скачивание трека/плейлиста падало на Android.** yt-dlp (2026.10.26 в APK) требует внешний JS-рантайм (deno/node/quickjs/bun) для извлечения YouTube: без него YouTube-клиенты деградируют до jsless-набора `visionos`, решение подписей (sig/n) падает («Some formats may be missing»), GVS-стримы не отдаются — потому и трек, и плейлист на телефоне завершались ошибкой, а история оставалась пустой (в БД пишутся ТОЛЬКО успешные загрузки — так же, как на ПК). В APK теперь бандлится лёгкий рантайм **QJS (QuickJS-ng 0.12.0, ~1,2 МБ)** под обе архитектуры: собирается NDK-clang'ом как PIE-исполнимый файл, пакуется в `jniLibs` с `useLegacyPackaging` (распаковка нативных библиотек с правом exec — единственное место, где Android разрешает исполнять файлы), а yt-dlp получает его явным путём через `js_runtimes: {'quickjs': {'path': ...}}`. Провайдер yt-dlp запускает `qjs --script file.js` и решает sig/n-челленджи локально, без сети.
- **«Яндекс Музыка» вылезала за экран** (v1.2.7): строка «точка + название» обёрнута в переносимый блок (`src-row`), метка «в разработке» — всегда своя строка, `overflow: hidden` на кнопке.

### Добавлено
- **Экспорт в Загрузки (Android).** Пользовательский запрос «нет возможности поменять папку назначения»: на Android произвольную папку приложениям выбирать нельзя (scoped storage), поэтому после успешной загрузки файлы копируются в системную папку **`Загрузки/ShipTones`** через MediaStore.Downloads (без разрешений, API 29+), с дедупликацией по имени и переключателем в Настройках (`Экспорт в Загрузки`, по умолчанию ВКЛ).
- **Кнопка «↗» в Истории** — системное «Поделиться» файла через FileProvider (`audio/*`), можно отправить трек в любое приложение (Telegram, Файлы и т.д.). В историю к колонкам добавлены `id`/`file_path` (в конец — совместимо с десктопным GUI).
- Версия приложения отображается в Настройки → О приложении (`ShipTones v1.2.8 (Android)`).

### Сборка
- `android/build.gradle`: `versionCode 4`, `versionName '1.2.8'`; `packagingOptions { jniLibs { useLegacyPackaging = true } }`; prebuilt `libqjs.so` (arm64-v8a, x86_64) в `android/src/main/jniLibs/`.

## [1.2.6] — фикс: ускорение скачивания треков и плейлистов

### Исправлено
- **Скачивание треков шло медленнее, чем нужно.** Главная причина — в yt-dlp-опциях YouTube-загрузчика стоял `'skip': ['dash', 'hls']`: пропуск манифестов ломал выбор аудио-only потока, и yt-dlp вынужден был брать «best» (видео+аудио прогрессивный поток). Трек качался «целиком» с видео на низком качестве — файл больше, скачивание медленнее, а запрошенное аудио-качество не достигалось. Манифесты DASH/HLS теперь доступны, `bestaudio/best` выбирает эффективный аудио-поток (WebM/Opus ~128–160 kbps).
- **Клиенты YouTube без PO-токена.** В yt-dlp >= 2025.11 у клиентов `web` и `android` PO-токен Google обязателен для HTTPS/DASH-стримов: без него YouTube троттлит выдачу до ~50–90 KB/s и отдаёт 403 (лишние ретраи). Список `player_client` заменён на актуальный набор yt-dlp `['tv_samsung', 'visionos', 'web']` — клиенты без PO-токена качают аудио-only Google Video-стримы без троттлинга, `web` остаётся fallback-ом (в фазе получения инфо список тоже синхронизирован).
- Таймаут сокета yt-dlp повышен с 15 до 30 секунд — меньше лишних ретраев и перезапусков при скачивании больших плейлистов или на медленных сетях.

### Изменено
- **Финальная фаза обработки плейлиста** (обложки + теги) после скачивания теперь выполняется **параллельно** (`ThreadPoolExecutor`) вместо последовательной — для плейлистов из десятков треков вся «скорость» обработки перестала добавлять время к общему циклу.
- **Параллельные фрагменты и ретраи**: `concurrent_fragment_downloads` 4→8 (кратный прирост на длинных треках/миксах с фрагментированными форматами), `buffersize` 1→4 МиБ, `fragment_retries` 2→5, `retries` 2→3, `skip_unavailable_fragments=False` — недоступный фрагмент больше не «тихо пропускается» (иначе получались дыры в аудио), а честно докачивается ретраем.
- **Параллельные потоки загрузки**: дефолт «Потоков загрузки одновременно» поднят с 3 до 4, верхний предел повышен с 5 до 8 (настройки, веб-интерфейс, мобильный бэкенд).

## [1.2.5] — фикс: обложки для автомобильных магнитол (LADA Granta / Enjoy Pro)

### Исправлено
- **Обложки не отображались в автомобильной магнитоле (LADA Granta, Granta Club / Enjoy Pro)** — треки, скачанные через ShipTones, не показывали обложку ни при проигрывании с USB/SD, ни при Bluetooth.
  - **ФИКС: имя файла обложки.** Обложка сохранялась рядом с аудиофайлом, но под именем `<Artist> - <Title>.jpg`, тогда как старые магнитолы ищут её по **каноническому имени `cover.jpg`**. Теперь пишется и `cover.jpg`, и `<Artist> - <Title>.jpg` (покрывает оба варианта поиска).
  - **ФИКС: недостающие зависимости в сборке.** В `release.yml` добавлены `--hidden-import=mutagen/...` и `--hidden-import=PIL/...` — в собранном `.exe` раньше могли не попасть `mutagen`/`Pillow` (нужны для встраивания JPEG в ID3/APIC и подготовки изображения), из-за чего весь блок обработки обложек молча пропускался (`HAS_MUTAGEN`/`HAS_PIL` выставлялись в `False`).
  - **ФИКС: краш при запуске exe.** `webapp.py` импортировал `open_folder` из `utils`, но самой функции не было — `ShipTones.exe` падал с `ImportError: cannot import name 'open_folder' from 'utils'` и не доходил до обработки обложек вовсе. Функция добавлена в `utils.py`.

### Изменено
- В лог загрузки добавлены причины пропуска обложки (`обложка не обработана` / `обложка не найдена (video_id)`) — теперь по `shiptones.log` видно, на каком этапе ломается встраивание.

## [1.2.4] — фикс: плейлисты снова скачиваются

### Исправлено
- **Плейлисты вообще не скачивались** (регрессия, вошедшая во все релизы после v1.1.0: v1.2.1–v1.2.3). Две независимые причины:
  - В режиме «Плейлист» в `yt-dlp` передавался `'playlistend': 0`. Для yt-dlp `0` — это КОНЕЦ ВЫБОРКИ на индексе 0 (формируется срез `1:0` → пусто), а «без ограничения» — это `None`/`-1`. Итог: yt-dlp возвращал 0 треков → «❌ Нет доступных треков». Файлы: `sources/ytmusic_source.py`, `sources/youtube_source.py`.
  - Раскрытие плейлиста было спрятано за проверкой `info.get('ie_key') == 'YoutubePlaylist'`, которая никогда не срабатывала: у ссылок `youtube.com/playlist?...` и `music.youtube.com/playlist?...` yt-dlp выбирает экстрактор `YoutubeTabIE`, т.е. `ie_key = 'YoutubeTab'` (проверено непосредственно на yt-dlp 2026.8.19). Из-за этого кнопка не раскрывалась: качался «один трек», у которого id плейлиста подставлялся в `watch?v=PL...` ( такого видео не существует) → ошибка, а фолбэк `ytsearch1:{заголовок кнопки}` качал случайный трек. Возвращена механика работавшей v1.1.0: кнопки раскрывается по наличию `entries` в результате, «Один трек» отрезается уже в Python.
- `APP_VERSION` в `config.py` остался «1.1.1» во всех релизах v1.2.x — автообновление бесконечно предлагало пользователям 1.2.x «обновиться» на v1.2.2. Поднято до `1.2.4` (не забудьте тег `v1.2.4` при выпуске).

### Проверка
- Офлайн-тест с подменённым yt-dlp: playlist-URL в режиме «Плейлист» → все треки раскрыты (`playlistend=None`), playlist-URL в режиме «Один трек» → ровно 1 трек (`playlistend=1`), обычная single-ссылка в режиме «Плейлист» → 1 трек.

- Обложка и расширенные теги не встраивались при загрузке одиночного видео (не плейлиста) — `_process_tags_and_covers` теперь одинаково работает и с плейлистом, и с одним треком.
- Событие `done` никогда не сообщало об ошибке или отмене — теперь несёт `{ok, canceled, error, stats}`, интерфейс показывает реальный результат вместо всегда «Загрузка завершена».
- При некоторых ранних завершениях `download()` событие `done` отправлялось дважды подряд (явно и через `finally`).
- Исключения в потоках загрузки (`ThreadPoolExecutor`) терялись молча — теперь логируются и учитываются в статистике ошибок.
- `touch_playlist()` помечал плейлист синхронизированным даже при отменённой загрузке.
- Отчёт о загрузке сохранялся в `BASE_DIR/logs` вместо `DATA_DIR/logs` — в `.exe` эта папка может быть недоступна для записи.
- Повторная обработка тегов/обложек проходила по ВСЕМ mp3-файлам в папке при каждом запуске (включая ранее скачанные) — теперь только по файлам текущей сессии.
- `INSERT OR REPLACE` в `save_playlist()`/`add_track()` сбрасывал `last_synced`/`id` при повторном сохранении — заменено на `UPSERT`.
- Пустой URL мог попасть в историю загрузок — добавлена проверка перед записью.
- Обложка растягивалась при встраивании (YouTube-превью не квадратные) — заменено на `ImageOps.fit()` с обрезкой по центру.
- `clean_filename()` мог оставлять висячий пробел после обрезки до 100 символов.
- Два разных трека с одинаковым «очищенным» именем файла могли конфликтовать — второй трек получает суффикс `(2)`, `(3)` и т.д.
- Проверка превью на YouTube делала полный `GET`-запрос вместо `HEAD` и пропускала валидные картинки без `Content-Length`.
- `detect_source()` (автоопределение источника по URL) был объявлен, но нигде не вызывался — подключён к `Api` и к полю ссылки в интерфейсе.
- `auto_update_ytdlp` был декларативной настройкой без эффекта — теперь реально проверяет обновления при старте (в фоновом потоке).
- Нет валидации `max_workers`/`quality`/`download_dir` при сохранении настроек — невалидные значения теперь отбрасываются или приводятся к границам.
- `_launch()` не был защищён от сбоя конструктора `Downloader` — интерфейс мог зависнуть в состоянии «идёт загрузка» навсегда.
- В `app.js`: добавлены `try/catch` вокруг вызовов `pywebview.api` в `start_download`/`init`, подтверждение перед удалением плейлиста, индикатор «Загрузка…» для истории и плейлистов.

### Удалено
- Настройки `normalize_volume`, `remove_silence`, `sync_enabled`, `sync_disk`, `sync_interval_hours` — были объявлены в конфиге и README, но никогда не были реализованы (фильтры закомментированы, планировщика синхронизации не существует).

### Известные ограничения
- VK Музыка и Яндекс Музыка — в разработке: у yt-dlp нет рабочего экстрактора для этих сервисов, реальная загрузка потребует реверс-инжиниринга их приватных API.

## [Unreleased] — stop, автообновление, изоляция источников

### Исправлено
- **Отмена загрузки теперь действительно останавливает её мгновенно.** Раньше кнопка «Стоп» проверялась только между файлами — yt-dlp всё равно докачивал начатый трек до конца. Теперь в `progress_hooks` на каждый тик прогресса проверяется отмена и поднимается `yt_dlp.utils.DownloadCancelled`, что обрывает скачивание текущего файла немедленно, а не в очереди.
- Отменённый на середине трек больше не засчитывается в статистику как «ошибка».

### Добавлено
- **Проверка обновлений приложения.** Кнопка «Проверить обновления» в Настройках → Обслуживание (рядом с «Обновить yt-dlp») сверяет версию с последним GitHub Release репозитория через публичный API. Если версия актуальна — тост «У вас установлена последняя версия». Если есть новее — сама скачивает новый `.exe`, готовит подмену старого файла и перезапускает приложение (замена происходит после выхода процесса — Windows не даёт перезаписать выполняющийся exe).
- Новый workflow `.github/workflows/release.yml`: пуш тега вида `v1.2.0` собирает exe и публикует его как GitHub Release. Чтобы выпустить версию: поднять `config.APP_VERSION` и запушить одноимённый тег.
- Версия приложения теперь видна в сайдбаре (берётся из `config.APP_VERSION`, а не захардкожена в HTML).
- Источники VK Музыка/Яндекс Музыка в интерфейсе помечены меткой «в разработке».

### Изменено — разграничение источников загрузки
- `Downloader.download()` больше не ведёт всю логику одним куском — теперь это диспетчер, который передаёт управление отдельному изолированному методу под источник: `_download_youtube` (единственный сейчас реально работающий, через yt-dlp), `_download_vk`, `_download_yandex`. VK/Яндекс сразу возвращают понятную ошибку «источник ещё не реализован» вместо попытки прогнать их через общий yt-dlp-путь, которая могла вести себя непредсказуемо. Сбой или будущая доработка одного источника не может затронуть код другого.
